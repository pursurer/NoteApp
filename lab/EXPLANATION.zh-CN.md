# NotesApp 数据流图与 STRIDE 讲解

NotesApp 在这个实验里是成绩管理系统。学生查看自己的成绩，教师查看课程并录入成绩，管理员管理用户。原图下方补充六个 STRIDE 问题和完整表格，便于沿着每条箭头检查风险。

读图时先看方向和编号。1 是学生登录，2 是请求成绩，3 是 Flask 返回会话与成绩；4、5 合并教师的请求与响应；6、7 合并管理员的请求与响应。这七条流跨越 TB1，即浏览器与 Flask 的信任边界。8 是 Flask 向 PostgreSQL 发送 SQL 读写，9 是数据库返回结果或完成状态，它们跨越 TB2。信任边界表示数据进入另一个控制范围后，需要检查身份、权限和输入，不代表已经部署防火墙。

完整表格按“编号｜发送方→接收方｜传输数据｜信任边界｜S｜T｜R｜I｜D｜E”排列。编号把表格行与图中箭头连接起来；发送方与接收方明确方向；传输数据（Data）说明登录信息、会话、成绩、SQL 等具体内容；信任边界（Boundary）指出这条流跨过 TB1 还是 TB2。后三部分分析须围绕该行的数据与边界，不能只罗列与箭头无关的漏洞。

对九条流逐一提出同样六问：S（身份冒充），能冒充用户或服务吗？T（篡改），能未经授权修改请求、返回或存储的数据吗？R（抵赖），能否否认操作，记录能证明是谁做的吗？I（信息泄露），不该看到的人会看到吗？D（拒绝服务），滥用是否影响正常服务？E（权限提升），普通用户能取得教师或管理员权限吗？每格写具体风险及其条件；不适用或尚未核验时明确标注。同一问题可涉及多类，但不必为每条流硬找六个漏洞。

例如第 1 行，登录 SQL 拼接输入，是源码支持的 T 风险；若因此绕过身份检查，还可能关联 S、E，但本次未验证绕过。第 2 行，成绩 API 没有检查成绩所有者，支持 I 风险；实际只读取学生自己的预置成绩，未验证读取他人记录或取得教师权限。第 5 行，评论模板关闭自动转义；若攻击者的脚本在教师浏览器执行，可能借教师权限操作，但本次没有测试脚本执行。合法管理员创建 admin 用户、普通响应元数据本身均不构成提权。

此次记录有 41 个普通 HTTP 请求，数据库摘要前后一致。成绩、用户管理和 Ping 表单未提交，没有攻击或压测；数据库流由源码重建。数据库 TLS 关闭是已核验配置，截获数据、资源耗尽及权限过宽仍须区分潜在场景与未验证项。紧凑图省略静态资源、日志、CSV 细节与 Ping 子进程，只覆盖九条主数据流。
